## 1. 已确认的架构基础

- PluginRuntime 管理一次运行中的发现、激活、有效 Contributions 和清理。
- 启动时发现并验证所有有效 Plugin，不意味着启动所有 host。只有显式激活才启动对应 host。
- 停用 Plugin 后，当前 catalog 立即移除其 Contributions；后续模型轮次不可继续使用这些 Contributions，并关闭对应 host。
- 工具使用 `plugin__tool` 命名，不覆盖内置工具。
- 同名项目配置覆盖全局配置。
- 安装和更新是显式操作，不由自然语言自动触发代码加载。
- 会话激活与停用不修改持久化 `enabled` 配置，需要审计记录。
- 工具、命令、技能和 hooks 最终归入同一 Plugin 生命周期。

## 2. broker 的含义与约束范围

`PluginCapabilityBroker` 是 Penhin 主程序提供的能力请求中介。Plugin 通过它请求文件读取、联网、凭据句柄或状态操作时，主程序检查授权后执行，并记录请求情况。

必须区分三种数据：

| 数据 | 含义 |
| --- | --- |
| manifest 声明 | Plugin 说自己需要哪些能力，是能力上限 |
| broker 授权记录 | 用户允许或拒绝该 Plugin 使用哪些受管能力 |
| 审计记录 | 实际发生的操作、请求与允许或拒绝结果 |

用户已接受当前阶段的信任模型：Plugin 来源必须可信。独立进程和 venv 不是操作系统级沙箱；Plugin 仍可能直接调用 Python 的文件、网络等功能绕过 broker。本文的授权规则只约束 broker 通道，不承诺限制 Plugin 的全部系统行为。

## 3. 已确认的授权规则

| 议题 | 确认结果 |
| --- | --- |
| 首次授权 | 首次激活展示所需 broker 能力，由用户确认并保存授权；未确认不自动授予 |
| 新增能力 | 新增能力再次确认；已有明确拒绝始终有效，不能被普通激活或更新覆盖 |
| 默认范围 | 默认按项目授权；全局安装不自动获得跨项目权限 |
| 部分授权 | 允许 Plugin 激活；被拒绝的 broker 请求返回明确权限错误 |
| 撤销时机 | 后续 broker 请求立即受新授权约束；已开始的请求允许结束，已完成操作不回滚 |
| 更新继承 | 同 Plugin、来源未变、无新增能力时沿用项目授权；新增能力确认，更换来源重新授权；明确拒绝继续有效 |
| 交互通道 | 有可用交互通道就请求确认；无通道则只使用已有授权，未授权能力返回需要交互授权的错误，不无限等待 |
| 后台任务 | 后台不等于不能交互；连接前台时可以转交授权请求 |
| 存储 | 授权保存在当前用户本机配置目录，按项目区分，不提交 Git；项目声明不能替用户批准 |
| 项目识别 | 同一 Git 仓库的 worktree 共享授权；独立 clone 和普通目录分别授权；Plugin 名称、来源仍须匹配 |
| 子代理 | 主代理按任务分配 Plugin 工具与 broker 能力，不能超过项目已有授权；新增授权由主会话处理 |

概念上，有效 broker 能力由 manifest、用户许可和当前任务限制共同决定，明确拒绝优先。项目允许某 Plugin 不等于每个子代理都自动获得它。

尚未确定授权文件格式、具体存储路径、来源等价判定算法或命令语法。不得把这些实现细节当作已获确认的产品规则。

## 4. Plugin Artifact、digest 与锁记录

Plugin Artifact 是供运行的一份确定的 Plugin 内容。digest 是根据相关文件路径和内容计算出的摘要，用于判断内容是否与锁定时一致。它不证明作者身份或代码安全。

已确认：

- 缺少有效锁记录时，该 Plugin 暂不可激活，提示显式安装或修复；其他 Plugin 和内置工具继续可用。
- 启动时不自动把当前目录内容接纳为新的锁定版本。
- 默认一次运行固定选定的 Artifact，普通更新只影响后续运行。
- **新增例外：用户显式执行 reload，可以让当前会话切换到新的 Artifact。** digest 校验仍需保留。

内容与锁不一致时是否统一拒绝普通激活，曾提出建议，但讨论随即转入 reload；不得把该细节标为已经单独确认。需要结合 reload 的接纳规则继续确定。

## 5. 最新决定：批量热重载所有 Plugin

用户明确选择直接重载所有 Plugin，不先做只重载指定 Plugin 的第一版。

已经确定的是批量范围的方向，以及显式 reload 可改变当前运行选定的 Artifact。最终命令名称、集合定义和事务语义仍未确认。讨论中使用 `/reload` 作为称呼，不应据此宣称完整 CLI 协议已经确定。

下列内容仅是此前建议，尚不能直接作为实现要求：等待正在执行的调用结束；保持原激活状态；准备失败保留旧版本；准备新版本后统一切换 host 与 Contributions。

批量重载不能悄悄推翻已确认的懒启动规则：重载所有 Plugin 不应被解释为获得启动所有 host 的授权。具体如何处理未激活 Plugin，留待下一轮确定。

## 7. 下次 grill 的继续位置

从批量 reload 开始，一次一个问题；以下是待讨论队列，不是已确认的答案：

1. **“所有 Plugin”的集合**：重新读取有效配置，还是沿用会话开始时的注册集合？新增、移除和禁用的 Plugin 如何处理？
2. **失败范围**：某 Plugin 新版本失败时，全部回滚，还是其他 Plugin 成功切换、失败项保留旧版本？
3. **在途调用**：等待结束、取消还是拒绝本次 reload？等待超时如何处理？
4. **激活状态**：是否保留原状态？未激活 Plugin 如何刷新 Artifact 而不启动 host？
5. **来源处理**：reload 仅接纳本地改动，还是也更新 Git/PyPI 来源？与显式 update 如何区分？
6. **授权与接纳顺序**：新增能力、更换来源、内容不匹配时，何时确认、写锁和发布新 catalog？
7. **host 状态**：旧 host 的会话状态是丢弃、迁移还是由 Plugin 自行恢复？
8. **审计与贡献切换**：如何记录前后 digest、部分失败；commands、skills、hooks 如何一起撤销和发布？

之后继续收敛全部 Contributions 的生命周期与审计，再总结整体约定供用户确认后实施。用户当前要求先交付文档，暂停提问。
